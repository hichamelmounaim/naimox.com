Git Commit Best Practices: Stop Writing Bad Messages

Look at the Git history of a personal project you wrote a year ago. Chances are, you will see a litany of messages reading: "fixed bug", "wip", "update", "finally working", and perhaps a frustrated "asdfasdf". When you are the only one working on a codebase, these lazy commit messages seem harmless. However, the moment you join a professional development team, your Git history ceases to be a personal scratchpad and becomes the single most important documentation tool for the entire project.

A well-maintained Git history allows a team to track down when a specific bug was introduced using git bisect, automatically generate release notes, and understand the context behind confusing code decisions long after the original author has left the company. Poor commit messages render these workflows impossible. In this guide, we will explore the professional standards for creating a clean, useful, and professional Git history.

The Concept of Atomic Commits

Before you even write a message, you need to understand what you are committing. The foundational rule of version control is the "Atomic Commit." An atomic commit is a single, complete, and indivisible unit of work. It should do exactly one thing, and it should do it completely.

If you spend an afternoon building a new login form, fixing a CSS bug in the footer, and refactoring a database utility function, you should not lump all those changes into a single commit with the message "updated UI and fixed db". You should make three separate commits. Why? Because if the database refactor breaks production, the team needs to be able to use git revert to undo the database changes without accidentally removing the new login form as well. Keep your commits small, focused, and independently reversible.

The Anatomy of a Professional Commit Message

A standard professional commit message consists of three parts: a subject line, an optional body, and an optional footer. They should be separated by blank lines.

1. The Subject Line (The Summary)

The subject line is the most important part. It is what appears when running git log --oneline and what reviewers see first on GitHub or GitLab. Follow these strict rules:

  • Capitalize the first letter. Treat it like the beginning of a sentence.
  • Do not end with a period. Space is valuable; punctuation is unnecessary.
  • Limit the length to 50 characters. If you cannot summarize the change in 50 characters, your commit is probably not atomic and needs to be split up.
  • Use the imperative mood. This is the most crucial rule. Write the message as if giving a command. Use "Add login validation" instead of "Added login validation" or "Adding login validation". A good test is to complete this sentence: "If applied, this commit will [your subject line]."

2. The Body (The Context)

While the subject line explains what changed, the body explains why it changed. The code itself shows how you did it, but only the commit message can explain the business logic or rationale behind the decision. Wrap the body text at 72 characters to ensure it renders correctly in all terminal environments. Use the body to explain what the previous behavior was, what the new behavior is, and why you made the switch.

3. The Footer (The Metadata)

The footer is reserved for tracking metadata. This is where you link the commit to your issue tracking system (Jira, Linear, GitHub Issues) using keywords like Closes #123 or Resolves TICKET-402. Many project management tools will automatically close the referenced ticket when the commit is merged into the main branch.

The "Conventional Commits" Standard

Many modern development teams have adopted the "Conventional Commits" specification. This is a lightweight convention on top of commit messages that provides an easy set of rules for creating an explicit commit history. It requires prefixing your subject line with a specific type, making it incredibly easy to parse the history programmatically to trigger automated semantic versioning and changelog generation.

The standard prefixes include:

  • feat: A new feature for the user.
  • fix: A bug fix for the user.
  • docs: Changes to the documentation only.
  • style: Formatting, missing semi-colons, etc. (no code change).
  • refactor: Refactoring production code (neither fixes a bug nor adds a feature).
  • test: Adding missing tests or correcting existing tests.
  • chore: Updating build tasks, package manager configs, etc.

An example of a Conventional Commit looks like this:

feat: add password strength meter to registration

When a user registers, they previously had no visual feedback
on the security of their password. This implements a visual
meter relying on the zxcvbn library to calculate entropy.

Resolves #842

Why Bother? The Long-Term Value

Writing good commit messages requires slowing down for an extra 60 seconds before typing git push. When you are rushing to finish a feature on a Friday afternoon, it feels like an annoying administrative burden. But software development is a team sport, and code is read far more often than it is written. A pristine Git history acts as a time machine, allowing developers to safely navigate and understand complex codebases years after the code was initially authored. Treat your commit history with the same respect you treat your production code.
